## 1. 개요/배경

식자재 유통사가 1,000개 이상 B2B 거래처를 대상으로 프로모션 이벤트를 운영하지만, 현재는 전화·엑셀·카톡 등 수기 채널로 참여를 받고 있어 (1) 참여 현황 집계가 안 되고 (2) 개인정보 동의 기록이 남지 않으며 (3) 추첨의 공정성·기록을 담보할 수 없다.

이 서비스는 **이벤트 등록 → 참여 → 룰렛 즉시 추첨 → 관리자 참여자 현황 조회**의 단일 플로우를 웹으로 옮긴다. 도메인 모델(이벤트 3종 참여 방식, 참여 대상 유형 3종, 참여신청 유일성, 가중치 추첨)은 도메인 정의서에서 이미 확정되었다.

**제약이 곧 배경이다: 1인 개발 / 3일.** 따라서 이 PRD의 핵심 산출물은 기능 목록이 아니라 **P0 최소 집합의 확정**이다. 1일차에 인증(회원가입/로그인)까지 끝내는 일정으로 잡으므로, 회원 로그인 참여와 비회원 참여 모두 P0에 포함한다. 마이페이지(참여 내역/정보 수정)·신청 취소처럼 "로그인 이후 부가로 확인/관리하는" 기능만 P1이다.

## 3. 범위 (우선순위)

도메인 정의서 9절 MVP 범위를 그대로 사용하되, **3일 안에 반드시 동작해야 하는 것(P0)** 과 **MVP 범위이지만 3일 내 미완성이어도 출시를 막지 않는 것(P1)** 으로 나눈다. 제외 항목은 도메인 정의서 9절 "제외"를 그대로 따른다.

| FR-1.1 | 회원가입(일반 참여자) | 1일차 인증 작업에 포함. 회원 로그인 참여(FR-1.4)의 전제조건 |

| FR-2.6 | 이벤트 삭제, 참여자 목록 엑셀 다운로드 | 조회 화면 복붙으로 버팀 |

### 제외
도메인 정의서 9절 "제외" 전체 + 추가로 다음도 이번 릴리스에서 만들지 않는다: 이메일 인증, 비밀번호 재설정(관리자 수동 처리), 관리자 권한 세분화, 감사 로그, 다국어, 접근성 대응, 이벤트 상세 조회수 집계(전환율 지표 자체를 두지 않음, 8절 참고), 테스트 자동화 스위트(금전·확률이 걸린 핵심 로직 자체 체크 2건 — 룰렛 가중치 추첨, 중복 신청 방지 분기 — 만 유지, 나머지 자동화 없음).

## 4. 기술 스택 및 아키텍처 개요

주어진 스택 그대로. 추가 제안 최소화.

| 레이어 | 선택 |
|---|---|
| 프론트엔드 | React 19, Zustand(로그인 상태 + 토큰 보관), TanStack Query(서버 상태 전부, 401 시 Refresh 재발급 후 재시도) |
| 백엔드 | Node.js + Express, `pg` 직접 쿼리 (ORM 없음) |
| DB | PostgreSQL 17 |
| 인증 | JWT Access Token(1시간) + Refresh Token(14일). **쿠키(HttpOnly) 미사용** — 두 토큰 모두 로그인/재발급 응답 바디로 내려주고 프론트가 보관(Zustand + localStorage persist)한다. Refresh는 서버 `refresh_tokens` 테이블에 해시로 저장해 로그아웃 시 폐기·재발급 시 회전(기존 토큰 삭제 후 신규 발급) 처리한다 |
| 배포 | 단일 서버(VM 1대), Express가 프론트 빌드 정적 서빙, Caddy 리버스 프록시로 자동 TLS, `pm2`로 프로세스 관리 |

**설계 원칙 (오버엔지니어링 금지)**
- 마이그레이션 툴 없이 `schema.sql` 1개 파일. 테이블은 users/events/prizes/entries/refresh_tokens 5개. 3일짜리 프로젝트에 스키마 버저닝은 불필요.
- 쿠키를 쓰지 않으므로 CORS credentials·SameSite·Secure 설정, 로컬 개발 시 cross-origin 쿠키 문제가 애초에 발생하지 않는다. 앱 부팅 시 localStorage에 Refresh Token이 있으면 즉시 `/auth/refresh`를 호출해 Access를 재발급하고(silent refresh), 그동안 라우팅을 잠깐 대기시킨다. 실패하면 로그아웃 상태로 취급한다.
- 재사용 감지 후 "전 기기 강제 로그아웃" 같은 고급 토큰 보안은 도입하지 않는다(3,000명 규모 내부 B2B 프로모션에는 과함). Refresh는 회전만 하고, 탈취 대응은 로그아웃(해당 토큰 폐기) 수준으로 충분하다.
- 중복 신청 방지는 앱 코드가 아니라 **DB UNIQUE 제약**으로 건다. 회원은 `(event_id, user_id)`, 비회원은 도메인 5절에 따라 이메일 1개로 정규화한 `(event_id, guest_email)`. 판정은 `INSERT ... ON CONFLICT DO NOTHING`으로 예외 없이 감지한다(5-project-principle.md 2절 — 예외 catch 방식은 PostgreSQL 트랜잭션을 abort시켜 같은 트랜잭션의 룰렛 추첨이 실패하므로 쓰지 않는다). 반환 행이 없을 때만 기존 레코드의 status를 읽어 "신청완료면 거부 / 취소 상태면 재신청 처리"로 분기한다(락 없이 DB 제약 + 조회만으로 충분).
- 룰렛 추첨은 참여신청과 **같은 트랜잭션**에서 처리(도메인 6절). 큐/워커/락 서비스 도입하지 않음.
- 이벤트 상태는 컬럼 저장 + 조회 시 시각 비교(lazy). **스케줄러/크론 없음**(도메인 6절이 이미 그렇게 정의함).
- 시크릿 관리: `.env` 1개 + `.gitignore` 등록. 필요한 값은 `DATABASE_URL` / `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` / `ADMIN_SEED_EMAIL` / `ADMIN_SEED_PASSWORD` 5개뿐. 별도 시크릿 매니저는 도입하지 않는다.
- API 에러 응답은 `{ "error": { "code": "STRING_CODE", "message": "사용자 노출용 문구" } }` 형식 하나로 통일한다. 프론트는 공통 토스트 1개로 표시. 최소 코드셋: `DUPLICATE_ENTRY`(중복 신청), `TARGET_TYPE_MISMATCH`(대상 유형 불일치), `EVENT_CLOSED`(종료된 이벤트), `CONSENT_REQUIRED`(미동의).
- **만들지 않는 것**: WebSocket/실시간 룰렛 동기화, 알림(이메일/SMS/푸시), 캐시 레이어(Redis), 파일 업로드/CDN, 마이크로서비스 분리, Docker 오케스트레이션, 상태관리 미들웨어/정규화 스토어, 이벤트 상세 조회수 로깅.

## 6. 일정 계획 (3일, 1인)

| 일차 | 작업 | 완료 기준 |
|---|---|---|
| **1일차** | DB 스키마 설계 및 마이그레이션(`schema.sql`: users/events/prizes/entries/refresh_tokens + UNIQUE 제약), 관리자 시드 INSERT(FR-1.0, bcrypt 해시), Express 뼈대, 인증 전체(회원가입 FR-1.1, 로그인/로그아웃 FR-1.2, Access·Refresh 발급/재발급, 인증 미들웨어), 이벤트 CRUD API(등록/수정/종료) + 경품 저장, 이벤트 목록 정렬 쿼리, 관리자 화면(로그인/이벤트 목록/이벤트 등록·수정) | 브라우저에서 관리자 로그인 → 룰렛 이벤트 등록(경품 포함) → 목록에서 확인 → 종료 처리까지 **관리자 화면만으로** 동작. 회원가입/로그인 API는 curl로 토큰 발급·재발급 확인 |
| **2일차** | 참여신청 API(회원 로그인 참여·비회원 입력 참여 분기, 동의·대상유형 3종·이벤트상태 검증, DUPLICATE_ENTRY 분기 포함 중복 처리), 룰렛 가중치 추첨을 참여 트랜잭션 내에서 확정, 참여신청 목록 API + 관리자 화면 연동, 공통 에러 응답 포맷 적용, 참여자 화면(이벤트 목록/상세/참여, 로그인·회원가입, 룰렛 결과) | 브라우저에서 회원 로그인 참여와 비회원 참여가 모두 성공하고 룰렛 결과 화면이 뜨며, 관리자 화면의 참여신청 목록에 두 건 모두 반영됨 |
| **3일차** | TanStack Query 401 인터셉터 + 부팅 시 silent refresh 마감, 참여자 화면 모바일 반응형 전체 적용, 실제 브라우저 통합 테스트 및 버그픽스, 배포(Caddy 리버스 프록시+TLS, pm2) | 실제 모바일 브라우저에서 회원 참여·비회원 참여·룰렛 확정·관리자 이벤트 종료까지 전체 플로우 통과 및 배포 완료 |

**버퍼 정책**: 3일차 오후까지 P0(FR-1.0~1.11)가 안 끝나면 P1(FR-2.x)은 전부 4일차 이후로 미룬다. P0 안에서 더 줄여야 한다면 희생 순서는 **이벤트 수정 화면의 진행중 필드별 제한 로직(등록만 되면 됨) → 룰렛 회전 애니메이션(결과 텍스트만 표시) → 참여자 반응형의 디테일 스타일링(레이아웃이 깨지지 않는 최소 수준까지는 유지)** 순이다. 인증(FR-1.0~1.2), 참여신청 핵심 플로우(FR-1.3~1.6), 관리자 이벤트 관리(FR-1.7~1.9), 결과 화면(FR-1.10)은 절단 대상이 아니다.

## 7. 리스크 및 트레이드오프

**의도적으로 안 하는 것과 그 이유**

| 생략/단순화 | 이유 |
|---|---|
| 마이페이지(참여 내역·정보 수정)·신청 취소만 P1로 후행 | 회원가입·로그인·회원 참여 자체는 1~2일차에 포함되어 핵심 플로우엔 영향 없음. "참여 후 다시 들어와서 확인/관리"하는 부가 기능만 미룸 |
| 알림(이메일/SMS) 발송 없음 | 도메인 9절 제외 확정. 대신 룰렛 결과 화면 + 캡처 안내가 결과 확인 경로 |
| 경품 재고 관리 없음 | 도메인 9절 제외. 가중치만으로 확률 제어. 실물 경품 소진 등 이상 상황은 **FR-1.8(이벤트 종료)로 즉시 참여를 멈춰 대응**(더 이상 endAt을 앞당기는 방식은 쓰지 않는다 — 도메인 6절상 진행중 상태의 endAt은 연장만 가능하므로 애초에 성립하지 않는 방법이었음) |
| 폼 제출형 후순위(P1) | 동적 폼 정의/렌더/검증은 3일 예산에서 가장 비싼 항목 대비 첫 이벤트 기여도가 낮음 |
| 마이그레이션 툴/ORM 없음 | 테이블 5개. `pg` + `schema.sql`로 충분. 도입 비용이 이득보다 큼 |
| HttpOnly 쿠키 미사용 | 이번 구현 범위에서 명시적으로 제외. 대신 Access/Refresh 모두 응답 바디로 내려 프론트가 보관 — CORS/SameSite/로컬 cross-origin 쿠키 이슈가 사라지는 대신, XSS 방어(입력값 이스케이프, CSP 기본 헤더)는 프론트 구현 시 지켜야 함 |
| 별도 세션 스토어(Redis) 없음 | Refresh Token은 테이블 1개(`refresh_tokens`)로 관리. 3,000명 규모에 별도 인프라는 과함 |
| Refresh 재사용 감지·전기기 강제 로그아웃 없음 | 회전(rotation)만 적용. 내부 B2B 프로모션 자산 특성상 고급 토큰 보안까지는 불필요 |
| 테스트 자동화 스위트 없음 | 룰렛 가중치 추첨과 중복 신청 방지에 대한 자체 체크만 남긴다. 금전·확률이 걸린 로직만 검증 대상 |
| 관리자 화면 반응형 없음 | 도메인 7절에서 이미 제외 |
| 접근성 대응 없음 | 요구사항에서 제외 명시 |

**리스크**
| 리스크 | 영향 | 대응 |
|---|---|---|
| 3일 내 P0 미완성 | 출시 지연 | 6절 희생 순서대로 절단(인증·참여신청·관리자 이벤트 관리·결과 화면은 절단 대상 아님) |

| 비회원 동일 인물 오식별(이메일 다르게 입력) | 중복 참여 발생 | 도메인 8절에서 이미 "시스템 한계"로 수용 결정됨. 추가 대응 없음 |

| 실물 경품 이상 상황(소진 등) | 초과 당첨 발생 | FR-1.8(이벤트 종료)로 관리자가 즉시 참여를 막음. 재고 관리 자체는 P1 이후 |
| Access Token이 localStorage에 노출(쿠키 미사용) | XSS 시 토큰 탈취 가능성 | 만료 1시간으로 노출 시간을 제한. React의 기본 이스케이프를 신뢰하고 사용자 입력을 `dangerouslySetInnerHTML` 등으로 직접 렌더링하지 않는다 |
| 개인정보 유출 | 법적 리스크 | 비밀번호 해시(bcrypt), TLS(Caddy 자동 발급), 관리자 API는 role 검증 필수, 보유기간(1년) 고지. **이 항목은 절대 간소화 대상 아님** |
