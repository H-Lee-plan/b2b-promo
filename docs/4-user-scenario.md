## 이 문서의 역할

**다루는 것**: 액터(비회원 참여자 / 회원 참여자 / 관리자)가 실제로 무엇을 하고, 시스템이 어떻게 반응하며, 사용자가 무엇을 보는지의 흐름. 정상 흐름(골든 패스)과 예외 흐름을 함께 다룬다. 각 시나리오는 QA가 그대로 테스트 케이스로 전환할 수 있도록 관련 FR/도메인 규칙을 상단에 명시한다.

**다루지 않는 것**
- 화면 디자인·와이어프레임·카피 확정안 (문구는 의도 전달용 예시일 뿐, 최종안 아님)
- 엔티티/필드/상태값/상태전이/비즈니스 규칙의 정의 자체 → **모두 도메인 정의서 4~8절이 근거**이며 여기서 재정의하지 않는다. 충돌 시 도메인 정의서가 우선한다.
- 우선순위 판단 → PRD 3절이 기준. 이 문서는 핵심 참여 플로우(FR-1.0~1.11)에서 실제로 발생하는 흐름을 중심으로 쓴다.
- API 스펙, DB 스키마 (PRD 4절)

**범위 원칙**: 3일/1인 제약(PRD 1절)을 반영해 핵심 참여 플로우에서 실제로 발생하는 흐름만 쓴다. 폼 제출형(FR-2.3)은 후행 구현 항목이라 시나리오를 작성하지 않는다.

# 1. 비회원 참여자

## S-1. 비회원이 룰렛 이벤트에 참여해 당첨 결과를 확인한다 (골든 패스)

**이 시나리오가 다루는 FR/도메인 규칙**
- FR-1.3(목록 조회·정렬), FR-1.4(상세+참여신청, 비회원 입력 참여, 동의, 대상유형 검증), FR-1.5(룰렛 게임형), FR-1.6(가중치 추첨·트랜잭션 내 즉시 확정), FR-1.10(결과 화면), FR-1.11(반응형)
- 도메인 6절 "신청완료 → 당첨/미당첨", 7절 "비회원은 개인정보 직접 입력 + 수집·이용 및 보유기간 동의", 4절 Entry(guestEmail/guestPhone/guestInfo/consentedAt/prizeId)

**전제조건**
- 이벤트 A: `targetType = 비회원 전용`(또는 `공통`), `participationType = 룰렛 게임형`, 경품 2건 이상 등록됨, 현재 시각이 `startAt` 이후 `endAt` 이전 → 조회 시점에 `진행중`으로 계산됨
- 사용자는 로그인하지 않은 상태, 모바일 브라우저로 접속

**흐름**
1. 사용자가 모바일 브라우저로 서비스에 접속한다. → 시스템은 이벤트 목록을 마감임박순(동률 시 등록순)으로 보여주고, 상단 노출 설정된 이벤트를 강조해 최상단에 배치한다. 각 카드에 상태 뱃지(진행중/종료)를 함께 표시한다.
2. 사용자가 이벤트 A 카드를 누른다. → 시스템은 상세 화면에 이벤트명·설명·마감일시를 표시하고, 대상 유형이 비회원 참여를 허용하므로 **비회원 개인정보 입력 폼**을 노출한다.
3. 사용자가 업체명·담당자 이름·이메일·연락처를 입력한다. → 시스템은 이메일 형식과 필수 입력 여부를 즉시 검증하고, 형식이 어긋나거나 값이 비어 있으면 해당 입력칸 아래에 안내를 띄운다. (연락처는 형식 검증 없이 필수값 여부만 확인한다.)
4. 사용자가 "개인정보 수집·이용 및 보유기간 동의" 체크박스를 읽는다. → 시스템은 동의 문구에 **보유기간(이벤트 종료일로부터 1년)** 을 함께 고지한다.
5. 사용자가 동의에 체크하고 "참여하기"를 누른다. → 시스템은 하나의 트랜잭션 안에서 (a) 이벤트 상태가 진행중인지 확인, (b) 대상 유형 허용 여부 확인, (c) 동의 여부 확인(`consentedAt` 기록), (d) `(eventId, guestEmail)` 중복 여부 확인, (e) 경품 목록을 weight 비율로 추첨해 1건 확정, (f) 참여신청을 `prizeId`와 상태(당첨/미당첨)와 함께 저장한다. (검증 순서는 실제 구현 순서와 동일 — 미동의와 중복이 동시에 해당하면 `CONSENT_REQUIRED`가 먼저 반환된다.)
6. 저장이 끝나면 시스템은 룰렛 결과 화면으로 이동해 회전 애니메이션을 1회 보여준 뒤 **서버가 이미 확정한 결과**를 표시한다. (애니메이션은 연출일 뿐 결과를 정하지 않는다.)
7. 결과 화면에 경품명과 함께 **"비회원은 결과를 다시 조회할 수 없으니 이 화면을 캡처해 두세요"** 안내가 표시된다. → 사용자는 화면을 캡처하고 종료한다.

**대안/예외 흐름**
- 3에서 필수 항목을 비우고 제출: 시스템은 서버 요청 없이 미입력 항목을 표시하고 진행을 막는다.
- 5에서 추첨 결과가 "미당첨" 경품인 경우: 참여신청 상태는 `미당첨`으로 저장되고, 결과 화면은 실패가 아니라 정상 결과로 "아쉽게도 미당첨입니다"를 표시한다(오류 토스트 아님).
- 5의 검증 실패는 각각 S-2(미동의), S-3(대상유형 불일치), S-4(중복), S-9/S-10(종료된 이벤트)로 이어진다.
- 6에서 네트워크가 끊겨 결과 화면 진입에 실패: 참여신청은 이미 서버에 확정 저장된 상태이므로, 사용자가 같은 이벤트에 다시 참여를 시도하면 재추첨이 아니라 **중복 신청으로 거부**된다(S-5 참고). 비회원은 재조회 경로가 없으므로 이 경우 관리자 문의로만 확인 가능하다 — 알림 발송이 범위 외(도메인 9절)임에서 오는 알려진 한계다.

## S-2. 비회원이 개인정보 동의를 하지 않아 참여가 거부된다

**이 시나리오가 다루는 FR/도메인 규칙**
- FR-1.4(동의 검증), 도메인 7절 "동의 없이는 어떤 참여 방식이든 신청이 성립하지 않는다", 8절 첫 번째 예외, PRD 4절 에러코드 `CONSENT_REQUIRED`

**전제조건**: S-1과 동일한 진행중 이벤트, 로그인하지 않은 사용자

**흐름**
1. 사용자가 이벤트 상세에서 개인정보를 모두 입력하지만, 동의 체크박스는 비워 둔 채 "참여하기"를 누른다.
2. → 시스템은 참여 버튼을 비활성 상태로 두거나, 눌렸을 경우 "개인정보 수집·이용에 동의해야 참여할 수 있습니다"를 표시하고 신청을 생성하지 않는다.
3. 사용자가 동의 체크박스를 확인하고 체크한다. → 참여 버튼이 활성화된다.
4. 사용자가 다시 "참여하기"를 누른다. → S-1의 5단계 이후 정상 흐름으로 이어진다.

**대안/예외 흐름**
- 클라이언트 검증을 우회해 미동의 상태로 API가 호출된 경우: 서버가 `CONSENT_REQUIRED`로 거부하고 어떤 참여신청 레코드도 생성하지 않는다. 프론트는 공통 토스트로 메시지를 표시한다. (클라이언트 비활성화는 UX, 실제 방어선은 서버다.)
- 사용자가 동의 문구 링크를 눌러 상세 고지를 확인한 뒤 돌아오는 경우: 이미 입력한 개인정보는 유지되어야 한다.

## S-3. 비회원이 회원 전용 이벤트에 참여를 시도해 거부된다

**이 시나리오가 다루는 FR/도메인 규칙**
- FR-1.4(대상 유형 검증 3종 전체), 도메인 7절 "참여 대상 유형에 맞지 않는 참여자는 신청할 수 없다", 8절 두 번째 예외, PRD 4절 에러코드 `TARGET_TYPE_MISMATCH`

**전제조건**: 이벤트 B는 `targetType = 회원 전용`, 상태 진행중. 사용자는 로그인하지 않은 상태.

**흐름**
1. 사용자가 이벤트 목록에서 이벤트 B 카드를 누른다. → 시스템은 상세 정보를 보여주되, 대상 유형이 회원 전용이므로 개인정보 입력 폼 대신 **"회원 전용 이벤트입니다. 로그인 후 참여해 주세요"** 안내와 로그인/회원가입 버튼을 표시한다.
2. 사용자가 "로그인" 버튼을 누른다. → 로그인 화면으로 이동하고, 로그인 성공 후 이벤트 B 상세로 되돌아온다.
3. 로그인한 사용자가 회원 자격으로 참여를 진행한다. → S-6의 참여 단계와 동일하게 이어진다.

**대안/예외 흐름**
- 사용자가 로그인하지 않고 참여 API를 직접 호출하는 경우(또는 로그인 상태가 만료된 채 요청되는 경우): 서버가 `TARGET_TYPE_MISMATCH`로 거부하고 참여신청을 만들지 않는다.
- 반대 방향(로그인한 회원이 `비회원 전용` 이벤트에 참여 시도): 동일하게 `TARGET_TYPE_MISMATCH`로 거부된다. 화면에는 "이 이벤트는 비회원 전용입니다" 안내를 표시한다. 회원이 로그아웃 후 비회원으로 참여하는 것은 시스템이 막지 않으며, 이때는 별개의 참여로 간주된다(비회원 식별은 이메일 기준, 도메인 8절).
- `공통` 이벤트: 로그인 상태면 회원 참여 폼, 비로그인 상태면 비회원 입력 폼이 노출되며 어느 쪽도 거부되지 않는다.

## S-4. 비회원이 같은 이메일로 중복 참여를 시도한다

**이 시나리오가 다루는 FR/도메인 규칙**
- FR-1.4(중복 방지), 도메인 5절 "(이벤트, 참여자) 조합당 참여신청은 유일", 7절 "비회원은 이메일 기준으로 동일 인물 판단", 8절 세 번째·다섯 번째 예외, PRD 4절 `DUPLICATE_ENTRY` 및 DB UNIQUE 제약 기반 처리

**전제조건**: 사용자는 이벤트 A에 `guestEmail = kim@corp.co.kr`로 이미 참여했고, 그 참여신청은 `당첨`(또는 `미당첨`) 상태로 존재한다. 이벤트 A는 여전히 진행중.

**흐름**
1. 사용자가 결과를 다시 보고 싶어 이벤트 A 상세로 돌아온다. → 시스템은 로그인 상태가 아니므로 이전 참여 사실을 미리 알 수 없고, 비회원 입력 폼을 그대로 보여준다.
2. 사용자가 이전과 동일한 이메일 `kim@corp.co.kr`을 포함해 정보를 입력하고 동의 후 "참여하기"를 누른다.
3. → 서버는 `(eventId, guestEmail)` UNIQUE 제약 위반을 감지하고, 기존 레코드의 상태를 조회해 **신청완료 이상(신청완료/당첨/미당첨)이므로 중복으로 판정**한다. 새 레코드를 만들지 않고 `DUPLICATE_ENTRY`로 거부한다.
4. → 사용자 화면에는 "이미 이 이벤트에 참여하셨습니다"가 표시되고, 룰렛은 다시 돌지 않는다.

**대안/예외 흐름**
- 기존 레코드가 `취소` 상태였던 경우: 새 레코드를 만들지 않고 기존 레코드를 `신청완료`로 되돌린다(도메인 6절·8절). 단 비회원은 취소 기능 대상이 아니므로 이 분기는 회원 시나리오에서만 실질적으로 발생한다.
- 사용자가 다른 이메일(`kim2@corp.co.kr`)로 다시 참여하는 경우: 시스템은 동일 인물임을 알 수 없으므로 **별개의 참여로 정상 처리**되고 룰렛이 다시 돌아간다. 이는 도메인 8절에서 "시스템 한계"로 이미 수용된 동작이며 버그가 아니다(PRD 7절 리스크 표에도 명시).
- 이벤트가 그 사이 종료된 경우: 중복 판정보다 이벤트 상태 검증이 먼저이며 `EVENT_CLOSED`로 거부된다.

## S-5. 비회원이 룰렛 결과에 불복해 재참여(재추첨)를 시도한다

**이 시나리오가 다루는 FR/도메인 규칙**
- FR-1.6(재추첨 불가), 도메인 6절 "확정 이후 재추첨을 허용하지 않는다", 8절 일곱 번째 예외

**전제조건**: 사용자는 이벤트 A에 참여해 `미당첨` 결과를 이미 확인했다.

**흐름**
1. 사용자가 결과 화면에서 다시 시도할 방법을 찾는다. → 결과 화면에는 "다시 돌리기" 같은 재시도 버튼이 **존재하지 않는다**. 결과와 캡처 안내, 이벤트 목록으로 돌아가는 링크만 있다.
2. 사용자가 브라우저 새로고침을 누르거나 뒤로 가기로 상세 화면에 돌아가 같은 이메일로 다시 참여를 시도한다. → S-4의 3단계와 동일하게 `DUPLICATE_ENTRY`로 거부되며, 새 추첨은 일어나지 않는다.
3. 사용자가 고객센터에 재추첨을 문의한다. → 운영 정책상 확정 결과는 변경하지 않는다. 관리자는 참여신청 목록에서 해당 건의 확정 경품과 신청 시각을 조회해 근거를 안내한다(FR-1.9).

**대안/예외 흐름**
- 참여 버튼 연타로 요청이 두 번 전송된 경우: 두 번째 요청은 UNIQUE 제약에 걸려 `DUPLICATE_ENTRY`가 되며, 추첨이 두 번 일어나거나 레코드가 두 건 생기지 않는다. 프론트는 제출 중 버튼을 비활성화해 사용자가 이 오류를 보는 상황 자체를 줄인다.

# 2. 회원 참여자

## S-6. 신규 회원이 가입 → 로그인 → 회원 전용 이벤트에 참여한다 (골든 패스)

**이 시나리오가 다루는 FR/도메인 규칙**
- FR-1.1(회원가입), FR-1.2(로그인/로그아웃), FR-1.3(목록), FR-1.4(회원 로그인 참여·동의·대상유형·중복), FR-1.5/1.6/1.10(룰렛인 경우)
- 도메인 7절 "회원은 별도 개인정보 입력 없이 기존 회원 정보와 개인정보 사용 동의만으로 참여", 회원가입 제약(이메일 형식·중복 불가, 비밀번호 8자 이상)

**전제조건**: 이벤트 B는 `targetType = 회원 전용`, 진행중. 사용자는 아직 계정이 없다.

**흐름**
1. 사용자가 이벤트 목록에서 이벤트 B를 열고, 회원 전용 안내를 보고 "회원가입"을 누른다.
2. 사용자가 이메일·비밀번호·업체명·담당자 이름·연락처를 입력하고 가입을 누른다. → 시스템은 이메일 형식, 이메일 중복 여부, 비밀번호 8자 이상을 검증한다. 통과하면 계정을 생성한다(비밀번호는 해시로 저장).
3. 사용자가 가입한 계정으로 로그인한다. → 시스템은 Access Token(1시간)과 Refresh Token(14일)을 응답으로 내려주고, 프론트가 이를 보관해 로그인 상태를 유지한다. 헤더에 로그인 사용자 표시가 나타난다.
4. 사용자가 이벤트 B 상세로 돌아온다. → 시스템은 로그인 상태이고 대상 유형이 회원 전용이므로 **개인정보 입력 폼 없이** 이벤트 정보와 "개인정보 사용 동의" 체크박스, 참여 버튼만 보여준다.
5. 사용자가 동의에 체크하고 "참여하기"를 누른다. → 시스템은 회원 정보로 참여신청을 생성하고 `consentedAt`을 기록한다. 이벤트 B가 단순 참여형이면 상태는 `신청완료`가 되고 참여 완료 화면을 보여준다. 룰렛 게임형이면 S-1의 5~7단계와 동일하게 추첨이 확정되고 결과 화면이 표시된다.
6. 사용자가 로그아웃한다. → 서버는 해당 Refresh Token을 폐기하고, 프론트는 보관 중인 토큰을 지운다.

**대안/예외 흐름**
- 2에서 이미 가입된 이메일 입력: "이미 가입된 이메일입니다"를 표시하고 가입을 진행하지 않는다. 비밀번호 재설정은 이번 범위에서 제외이므로(PRD 3절), 안내는 관리자 문의로 유도한다.
- 2에서 비밀번호가 8자 미만: 입력칸 아래에 최소 길이 안내를 표시한다.
- 3에서 비밀번호를 틀림: "이메일 또는 비밀번호가 올바르지 않습니다"를 표시한다(어느 쪽이 틀렸는지는 구분하지 않는다). 로그인 시도 횟수 제한(FR-2.5)은 이 시나리오 범위 밖이라 걸지 않는다.
- 5에서 Access Token이 만료된 상태로 참여를 누름: 프론트가 Refresh Token으로 자동 재발급 후 요청을 재시도하므로 사용자는 실패를 보지 않는다. 재발급도 실패하면 로그아웃 상태로 전환되고 로그인 화면으로 안내한다.
- 5에서 동일 회원이 같은 이벤트에 재차 참여: `(eventId, userId)` 기준으로 `DUPLICATE_ENTRY` 거부(S-4와 동일 규칙).
- 앱을 껐다 다시 연 경우: 부팅 시 저장된 Refresh Token으로 조용히 재발급을 시도하며, 그동안 화면 전환이 잠시 대기한다. 실패하면 비로그인 상태로 시작한다.

## S-7. 회원이 룰렛 참여신청을 취소하려다 취소 불가를 확인한다

**이 시나리오가 다루는 FR/도메인 규칙**
- FR-2.1(마이페이지 조회), FR-2.2(취소/재신청) — 마이페이지 화면은 후행 구현 항목이지만 "룰렛은 취소 불가"라는 규칙 자체는 핵심 참여 로직에서도 지켜져야 한다
- 도메인 6절 "룰렛 게임형은 취소할 수 없다", 8절 여덟 번째 예외, PRD 5절 "룰렛 게임형은 취소 버튼 자체를 노출하지 않음"

**전제조건**: 회원이 (a) 룰렛 이벤트 A에 참여해 `당첨` 상태, (b) 단순 참여 이벤트 C에 참여해 `신청완료` 상태인 두 건을 보유. 두 이벤트 모두 진행중. 마이페이지가 구현된 상태.

**흐름**
1. 회원이 로그인 후 마이페이지 → 참여 내역을 연다. → 시스템은 참여한 이벤트 목록과 각 건의 상태(신청완료/취소/당첨/미당첨), 룰렛 건의 경품명을 함께 보여준다.
2. 회원이 룰렛 이벤트 A 건을 취소하려고 버튼을 찾는다. → **취소 버튼이 없다.** 대신 "룰렛 이벤트는 추첨 결과가 확정되어 취소할 수 없습니다" 안내가 표시된다.
3. 회원이 단순 참여 이벤트 C 건으로 이동한다. → 진행중 상태의 단순 참여형이므로 취소 버튼이 노출된다.
4. 회원이 이벤트 C의 취소를 누르고 확인한다. → 시스템은 새 레코드를 만들지 않고 기존 참여신청의 상태를 `취소`로 전환한다. 목록의 상태 뱃지가 `취소`로 바뀐다.
5. 회원이 마음을 바꿔 이벤트 C에 다시 참여한다. → 시스템은 기존 레코드를 `신청완료`로 되돌린다(새 레코드 생성 없음).

**대안/예외 흐름**
- 2에서 사용자가 취소 API를 직접 호출하는 경우: 서버가 룰렛 게임형임을 확인하고 거부한다. UI에 버튼이 없는 것은 편의일 뿐 방어선은 서버다.
- 4에서 이벤트가 그 사이 종료된 경우: 종료된 이벤트의 참여신청은 취소·재신청이 모두 불가하므로 `EVENT_CLOSED`로 거부되고 "종료된 이벤트는 취소할 수 없습니다"가 표시된다(도메인 6절·8절).
- 비회원이 취소를 원하는 경우: 비회원은 취소 기능 대상이 아니므로 마이페이지 경로 자체가 없다. 관리자 문의로만 처리한다.

# 3. 관리자

## S-8. 관리자가 룰렛 이벤트를 등록·운영하다 조기 종료한다 (골든 패스)

**이 시나리오가 다루는 FR/도메인 규칙**
- FR-1.0(관리자 계정 시딩), FR-1.2(로그인), FR-1.7(이벤트 등록/수정 + 경품 등록), FR-1.8(조기 종료), FR-1.9(참여신청 목록)
- 도메인 6절 "룰렛은 경품 1건 이상이어야 진행중 전환 가능", "진행중에는 targetType·participationType·startAt 수정 불가, endAt은 연장만", 7절(경품 weight 1 이상), PRD 7절 "경품 재고 관리가 없으므로 이상 상황 대응은 이벤트 종료가 유일한 수단"

**전제조건**: 관리자 계정이 DB 시드로 생성되어 있다(앱 내 관리자 가입 경로는 없음). 관리자는 데스크톱 브라우저로 백오피스에 접속한다(관리자 화면은 반응형 대상 아님).

**흐름**
1. 관리자가 백오피스 로그인 화면에서 시드 계정으로 로그인한다. → 시스템은 role이 관리자인지 확인하고 이벤트 목록 화면으로 이동시킨다.
2. 관리자가 "이벤트 등록"을 누른다. → 이벤트명·설명·참여 대상 유형(공통)·참여 방식(룰렛 게임형)·시작/마감 일시·상단 노출 토글 입력 폼이 열린다.
3. 관리자가 참여 방식으로 "룰렛 게임형"을 선택한다. → 시스템은 경품 입력 영역을 노출한다. 관리자가 경품명과 가중치를 행 단위로 추가한다(예: 상품권 1, 커피쿠폰 5, 미당첨 94). 가중치는 1 이상의 정수여야 하며 합계 대비 비율이 확률이 된다.
4. 관리자가 저장한다. → 시스템은 이벤트를 `등록` 상태로 저장하고 경품 목록을 함께 저장한다. 목록 화면에 새 이벤트가 나타난다.
5. 시작 일시가 지나면, 별도의 배치 없이 조회·참여 시점에 현재 시각과 `startAt`을 비교해 이벤트가 `진행중`으로 계산된다. 참여자 화면 목록에도 진행중으로 노출된다.
6. 참여가 들어오는 동안 관리자가 이벤트 목록에서 참여자 수를 확인하고, 이벤트를 눌러 참여신청 목록을 연다. → 시스템은 회원/비회원 구분, 신청 시각, 동의 시각, 확정 경품을 표 형태로 보여준다.
7. 실물 경품이 예상보다 빨리 소진되는 문제가 발생한다. 관리자가 이벤트 목록에서 해당 이벤트의 **"종료"** 버튼을 누르고 확인한다. → 시스템은 이벤트 상태를 `종료`로 전환한다.
8. → 종료 직후 들어오는 신규 참여 요청은 다음 요청부터 즉시 `EVENT_CLOSED`로 거부된다(lazy 계산이므로 반영 지연 없음). 관리자는 참여신청 목록의 건수가 더 이상 늘지 않는 것으로 확인한다(S-9).

**대안/예외 흐름**
- 3에서 경품을 한 건도 등록하지 않고 룰렛 이벤트를 진행중으로 만들려는 경우: 시스템은 경품이 1건 이상이어야 진행 가능함을 안내하고 막는다(도메인 6절). 경품 없이 룰렛 참여가 들어오는 상황을 원천 차단하기 위함이다.
- 3에서 가중치에 0 또는 음수를 입력: 1 이상의 정수만 허용된다는 안내를 표시한다.
- 진행중 상태에서 관리자가 참여 대상 유형·참여 방식·시작일시를 바꾸려는 경우: 해당 필드는 수정 불가로 비활성화되고, 이벤트명·설명·상단 노출·마감일시(연장만)만 수정 가능하다.
- 7의 대안으로 마감일시를 앞당겨 참여를 멈추려는 시도: `endAt`은 진행중에 연장만 허용되므로 성립하지 않는다. 참여를 즉시 멈추는 수단은 "종료" 버튼 하나뿐이다.
- 종료 처리 이후 이벤트를 다시 진행중으로 되돌리는 기능은 없다. 잘못 종료했다면 새 이벤트를 등록해야 한다. (되돌리기는 범위 외 — 상태 전이는 등록 → 진행중 → 종료 단방향.)

## S-9. 관리자가 종료된 이벤트에 신규 참여가 없는지 참여신청 목록에서 확인한다

**이 시나리오가 다루는 FR/도메인 규칙**
- FR-1.8(종료), FR-1.9(참여신청 목록 조회), 도메인 6절 "종료된 이벤트는 신규 참여신청을 받지 않는다", 8절 여섯 번째 예외, PRD 4절 `EVENT_CLOSED`, PRD 8절 지표 "종료 요청 후 신규 참여 차단까지 지연 = 즉시"

**전제조건**: S-8의 7단계에서 이벤트 A가 방금 종료 처리되었다. 종료 직전까지 참여신청 148건이 쌓여 있다.

**흐름**
1. 관리자가 이벤트 목록에서 이벤트 A의 상태 뱃지가 `종료`로 바뀐 것을 확인하고, 참여자 수 148건을 메모한다.
2. 관리자가 이벤트 A의 참여신청 목록을 연다. → 시스템은 148건을 신청 시각 순으로 보여준다. 각 행에는 회원/비회원 구분, 업체명·담당자·이메일·연락처, 동의 시각, 확정 경품, 상태가 표시된다.
3. 관리자가 잠시 후 목록을 새로고침한다. → 건수는 여전히 148건이다. 종료 이후 시각의 신청 레코드가 존재하지 않음을 확인한다.
4. 관리자가 검증을 위해 참여자 화면에서 이벤트 A 상세를 열어본다. → 상태 뱃지가 `종료`로 표시되고, 참여 버튼이 비활성화되거나 "종료된 이벤트입니다" 안내로 대체되어 참여 자체가 시작되지 않는다.
5. 관리자가 이 상태에서 참여를 강제 시도한다(예: 종료 직전 화면을 열어 둔 탭에서 참여 버튼 클릭). → 서버가 `EVENT_CLOSED`로 거부하고, 목록 건수는 그대로 148건이다.

**대안/예외 흐름**
- 종료 처리와 참여 요청이 거의 동시에 발생한 경우: 참여 트랜잭션 시작 시점의 이벤트 상태 판정을 기준으로 결정되며, 종료 이후 판정된 요청은 모두 거부된다. 경계에서 1~2건이 종료 시각 직전으로 기록되는 것은 정상이다(집계 시 종료 시각과 마지막 신청 시각을 비교해 확인).
- 목록에 표시할 참여신청이 0건인 이벤트: "참여신청이 없습니다" 빈 상태를 표시한다(오류 아님).
- 명단 엑셀 다운로드: 이 시나리오 범위에는 없다(FR-2.6은 별도 화면으로 후행 제공). 그 전까지 관리자는 화면 표에서 복사해 사용한다.
- 건별 동의 보유 메모 작성: 별도 관리자 화면(FR-2.4)에서 후행 제공한다. 동의 시각(`consentedAt`)은 참여 시 자동 기록되므로 법적 기록 자체는 이미 남아 있다.

# 4. 공통

## S-10. 참여자가 마감일자가 지나 자동 종료된 이벤트를 목록에서 본다

**이 시나리오가 다루는 FR/도메인 규칙**
- FR-1.3(목록 조회·정렬), FR-1.4(이벤트 상태 검증), 도메인 6절 "진행중 → 종료는 배치 없이 조회/참여 시점에 현재 시각과 endAt을 비교해 lazy 계산", PRD 4절 "스케줄러/크론 없음", `EVENT_CLOSED`

**전제조건**: 이벤트 D는 어제 23:59가 `endAt`이고, DB의 status 컬럼은 아직 `진행중`으로 저장되어 있다(자동 갱신 배치가 없으므로). 사용자는 오늘 접속한다.

**흐름**
1. 사용자가 이벤트 목록을 연다. → 시스템은 조회 시점의 현재 시각과 각 이벤트의 `startAt`/`endAt`을 비교해 상태를 계산한다. 이벤트 D는 `endAt`이 지났으므로 **컬럼 값과 무관하게 `종료`로 표시**된다.
2. 이벤트 D는 목록에서 사라지지 않고 `종료` 뱃지를 단 채 마감임박순 정렬 규칙에 따라 배치된다. → 사용자는 "아, 이건 이미 끝났구나"를 목록에서 바로 알 수 있다.
3. 사용자가 이벤트 D를 눌러 상세를 연다. → 이벤트 정보는 볼 수 있지만 참여 영역은 "종료된 이벤트입니다" 안내로 대체되고 참여 버튼이 동작하지 않는다.
4. 사용자가 목록으로 돌아가 진행중인 다른 이벤트에 참여한다. → S-1 또는 S-6의 흐름으로 이어진다.

**대안/예외 흐름**
- 사용자가 마감 직전에 상세 화면을 열어 두었다가 마감 이후 참여 버튼을 누른 경우: 화면은 아직 진행중으로 보이지만 서버가 참여 시점에 다시 상태를 계산해 `EVENT_CLOSED`로 거부한다. 화면에는 "이벤트가 종료되었습니다" 안내가 뜨고, 새로고침하면 종료 상태로 갱신된다. **화면 표시가 아니라 서버 판정이 기준이다.**
- 아직 `startAt`이 도래하지 않은 이벤트: 같은 방식으로 `등록` 상태로 계산되어 참여할 수 없다. 목록에는 노출하되 참여 버튼을 활성화하지 않는다.
- 관리자가 마감일시를 연장한 경우: 다음 조회부터 즉시 다시 진행중으로 계산된다(별도 재개 처리 불필요). 단 관리자가 "종료" 버튼으로 명시 종료한 이벤트는 endAt과 무관하게 종료 상태를 유지한다.
