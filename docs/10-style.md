## 1. 디자인 원칙

이 프로젝트는 B2B 내부 참여형 서비스다. 화려함보다 **신뢰감과 즉각적인 반응**이 우선한다. 아래 4가지로 모든 판단 기준을 압축한다.

1. **명확함이 미니멀보다 우선한다.** 화면을 비우는 것이 목적이 아니라, 가장 중요한 것(참여 버튼, 룰렛 결과, 마감 뱃지)이 가장 먼저 보이게 하는 것이 목적이다. 위계는 크기·굵기·여백 세 가지 조합으로만 만든다.
2. **되돌릴 수 없는 행동에만 확인을 요구한다.** 이벤트 종료·삭제처럼 되돌릴 수 없는 액션만 확인 다이얼로그를 거친다. 그 외 모든 곳에서 확인창을 남발하면 사용자가 확인창 자체를 무시하게 된다.
3. **반응은 누르는 즉시, 결과는 짧게.** 버튼은 누르는 순간(`:active`) 반응하고, UI 애니메이션은 300ms를 넘기지 않는다. 예외는 룰렛 결과 연출 1곳뿐이다(4번 참고).
4. **자주 보는 것일수록 덜 움직인다.** 하루에도 여러 번 보는 요소(관리자 테이블, 로그인 폼)는 애니메이션을 최소화하고, 어쩌다 한 번 보는 요소(룰렛 결과, 최초 참여 완료)에만 연출을 허용한다.

## 2. 색상

CSS 커스텀 프로퍼티로 선언하고 다크모드는 도입하지 않는다(요구사항에 없음, 도메인 정의서 9절 "제외" 원칙과 동일하게 지금 필요하지 않은 것은 만들지 않는다).

```css
:root {
  /* 중립(zinc 스케일) */
  --color-gray-50:  #FAFAFA;
  --color-gray-100: #F4F4F5;
  --color-gray-200: #E4E4E7;
  --color-gray-300: #D4D4D8;
  --color-gray-400: #A1A1AA;
  --color-gray-500: #71717A;
  --color-gray-600: #52525B;
  --color-gray-700: #3F3F46;
  --color-gray-800: #27272A;
  --color-gray-900: #18181B;

  /* 브랜드 강조(버튼/링크/진행중 상태) */
  --color-primary-50:  #EEF2FF;
  --color-primary-500: #6366F1;
  --color-primary-600: #4F46E5;
  --color-primary-700: #4338CA;

  /* 의미색 */
  --color-success-500: #16A34A; /* 저장/성공 토스트 */
  --color-danger-500:  #DC2626; /* 에러 토스트, 삭제 버튼 */
  --color-warning-500: #D97706; /* 주의(예: weight 검증 경고) */
  --color-amber-500:   #F59E0B; /* 당첨(WON) 강조 전용 */

  --color-bg:      #FFFFFF;
  --color-surface: var(--color-gray-50);
  --color-border:  var(--color-gray-200);
  --color-text:    var(--color-gray-900);
  --color-text-muted: var(--color-gray-500);
}
```

### 상태값 → 색상 매핑 (도메인 정의서 2절 Enum과 1:1 고정)

| Enum | 값 | 색상 | 비고 |
|---|---|---|---|
| `EVENT_STATUS` | `SCHEDULED`(등록) | `--color-gray-500` on `--color-gray-100` | 아직 시작 전 |
| | `ONGOING`(진행중) | `--color-primary-600` on `--color-primary-50` | 유일하게 참여 가능한 상태 |
| | `CLOSED`(종료) | `--color-gray-400` on `--color-gray-100` | lazy 계산 결과도 동일하게 표시(S-10) |
| `ENTRY_STATUS` | `APPLIED`(신청완료) | `--color-primary-600` | |
| | `CANCELED`(취소) | `--color-gray-400`, 텍스트 취소선 없이 muted 처리만 | 재신청 가능함을 암시(단정적 취소선 금지) |
| | `WON`(당첨) | `--color-amber-500` (배지 배경 채움) | 유일하게 "채워진" 배지 — 당첨은 시각적으로 튀어야 함 |
| | `LOST`(미당첨) | `--color-gray-500` | 오류가 아닌 정상 결과이므로 `--color-danger-500` 사용 금지(4절 룰렛 결과 참고) |

색은 상태 하나당 하나로 고정한다. 화면마다 다른 색을 쓰지 않는다 — 프로젝트 원칙 3절의 "Enum 상수 1:1 고정"과 같은 이유다.

## 3. 타이포그래피

Pretendard 웹폰트를 CDN(jsdelivr)으로 로드하고, 미로드 시에는 기존 시스템 폰트로 자연스럽게 폴백한다(v1.4 — 초기엔 "웹폰트 로딩 없음" 방침이었으나 리스킨 과정에서 한글 가독성·완성도를 위해 변경).

```css
:root {
  --font-sans: "Pretendard Variable", Pretendard, -apple-system, BlinkMacSystemFont, "Segoe UI",
    "Malgun Gothic", "Apple SD Gothic Neo", Roboto, Helvetica, Arial, sans-serif;
}
body { font: 400 1rem/1.6 var(--font-sans); }
```

| 토큰 | 크기 | 굵기 | line-height | letter-spacing | 용도 |
|---|---|---|---|---|---|
| `--text-display` | `clamp(1.5rem, 4vw, 2rem)` | 700 | 1.2 | `-0.01em` | 이벤트 상세 제목, 룰렛 결과 경품명 |
| `--text-h1` | `1.5rem`(24px) | 700 | 1.3 | `-0.01em` | 페이지 제목 |
| `--text-h2` | `1.25rem`(20px) | 600 | 1.35 | 0 | 섹션 제목, 카드 제목 |
| `--text-body` | `1rem`(16px) | 400 | 1.6 | 0 | 본문, 입력값 |
| `--text-small` | `0.875rem`(14px) | 400 | 1.5 | 0 | 보조 설명, 테이블 셀 |
| `--text-caption` | `0.75rem`(12px) | 500 | 1.4 | `0.01em` | 배지, 타임스탬프 |

큰 글자는 자간을 좁히고 작은 글자는 살짝 넓힌다(apple-design 15절) — 표에 이미 반영되어 있으니 값을 고정값 하나로 통일하지 않는다.

## 4. 간격 · 레이아웃

4px 배수의 단일 스케일만 쓴다. 중간 크기를 임의로 추가하지 않는다.

```css
:root {
  --space-1: 4px;  --space-2: 8px;  --space-3: 12px; --space-4: 16px;
  --space-5: 24px; --space-6: 32px; --space-7: 48px; --space-8: 64px;
}
```

- **컨테이너 최대 폭**: 참여자 화면 `720px`(단일 컬럼 위주, 와이어프레임 1·2·3절), 관리자 화면 `1120px`(테이블 위주, 데스크톱 고정).
- **브레이크포인트는 `768px` 하나만** 쓴다(프로젝트 원칙 FE-10과 동일). 태블릿 전용 중간 단계를 만들지 않는다.
- **관리자 화면은 반응형 대상이 아니다**(PRD 5절) — 데스크톱 폭 그대로 고정하고 좁은 화면 대응 코드를 넣지 않는다.

## 5. 모서리 · 그림자

레벨을 2개까지만 둔다. 카드/모달용 큰 그림자 하나, 그 외엔 그림자를 쓰지 않는다.

```css
:root {
  --radius-sm: 8px;    /* 버튼, 인풋 */
  --radius-md: 12px;   /* 카드 */
  --radius-full: 999px;/* 배지, 필 버튼 */

  --shadow-sm: 0 1px 3px rgba(24, 24, 27, 0.08), 0 1px 2px rgba(24, 24, 27, 0.04);
  --shadow-md: 0 10px 25px -5px rgba(24, 24, 27, 0.1), 0 8px 10px -6px rgba(24, 24, 27, 0.06); /* 모달, 드롭다운 */
}
```

## 6. 컴포넌트 패턴

### 버튼

```css
.button {
  border-radius: var(--radius-sm);
  padding: var(--space-3) var(--space-5);
  font: 600 var(--text-body)/1 var(--font-sans);
  transition: transform 160ms var(--ease-out), opacity 160ms var(--ease-out);
}
.button:active { transform: scale(0.97); } /* 누르는 즉시 반응 — emil-design-eng */
.button:disabled { opacity: 0.5; }
```

- Primary(참여하기, 저장): `--color-primary-600` 배경, 흰 글자.
- Danger(이벤트 삭제, 종료): `--color-danger-500` 배경 — **삭제/종료는 항상 확인 다이얼로그를 거친 뒤에만 이 버튼이 실행된다**(1절 원칙 2).
- Secondary(취소, 뒤로): 테두리만(`--color-border`), 배경 없음.
- 키보드로 반복 트리거되는 액션(폼 내 Tab 이동, Enter 제출)에는 추가 애니메이션을 넣지 않는다 — 눌림 피드백(`:active`)만으로 충분하다.

### 입력 필드 (로그인/회원가입/비회원 참여 폼/폼 제출형)

- 포커스 시 `border-color: var(--color-primary-500)` + `outline: 2px solid var(--color-primary-100)` (접근성 최소 기준, 9절 참고). 색만 바꾸고 크기/위치는 움직이지 않는다.
- 검증 실패 메시지는 입력칸 **바로 아래**, `--text-small` + `--color-danger-500`로 즉시 표시한다(S-6 "비밀번호 8자 미만" 등 — 제출 후가 아니라 입력 중 검증).

### 상태 배지 (이벤트 상태 / 참여신청 상태)

```css
.badge {
  display: inline-flex;
  align-items: center;
  border-radius: var(--radius-full);
  padding: var(--space-1) var(--space-3);
  font: 500 var(--text-caption)/1 var(--font-sans);
}
```
2절의 상태→색상 표를 그대로 적용한다. 배지 색으로만 상태를 구분하지 않는다 — 텍스트 라벨(예: "진행중", "당첨")을 항상 함께 표시해 색약 사용자도 구분 가능하게 한다.

### 카드 (이벤트 목록 카드)

- `--radius-md` + `--shadow-sm`. 상단 노출(`isPinned`) 이벤트만 `--color-primary-500` 1px 테두리를 추가로 준다 — 그림자 단계를 늘리지 않고 테두리 하나로 강조를 표현한다.
- 호버 시(데스크톱, `hover: hover` 미디어 쿼리로 터치 기기 오탐 방지): `box-shadow: var(--shadow-md)`로 전환, 120ms.

### 테이블 (관리자 참여신청 목록)

- 애니메이션 없음. 정렬·필터 변경 시 즉시 리렌더한다 — 관리자가 하루에도 여러 번 보는 화면이라 모션이 오히려 방해가 된다(1절 원칙 4, emil-design-eng "100+회/일 → 애니메이션 없음").
- 짝수 행에 `--color-surface` 배경으로 가독성만 확보하고, 그 외 장식을 더하지 않는다.

### Toast (공통 에러/성공 표시, FR 전역 7개 에러 코드 + 성공 메시지)

- 화면 우측 하단 고정, 한 번에 1개만(여러 개 쌓임 없음 — 오버엔지니어링 금지, 이 프로젝트 규모에 스택형 토스트는 불필요).
- 진입/퇴장은 `transform: translateY(100%) → translateY(0)` + `opacity`, **키프레임이 아니라 CSS transition**으로 구현한다(연속으로 여러 에러가 뜰 수 있어 중간에 끊기고 재시작될 수 있음 — emil-design-eng "빠르게 반복 트리거되는 요소는 keyframes 대신 transition").
- `duration: 250ms`, `--ease-out`. 자동 닫힘 4초, 에러는 사용자가 직접 닫을 때까지 유지(읽기 전에 사라지면 안 됨).
- 직접 만든 컴포넌트 1개로 충분하다(PRD·프로젝트 원칙에 이미 확정된 범위). **Sonner 같은 토스트 전용 라이브러리는 지금 도입하지 않는다** — 에러 코드 7종을 한 형태로만 보여주면 되는 단순한 요구라 라이브러리 도입 비용이 이득보다 크다. 추후 다중 토스트/실행취소(undo) 액션 등이 실제로 필요해지면 그때 `pick-ui-library` 스킬의 권장대로 Sonner 도입을 재검토한다.

### 동의 체크박스 (`ConsentCheckbox`)

- 체크 전에는 참여 버튼이 `disabled` 상태(흐림 처리, 클릭 자체가 안 됨) — 별도 애니메이션 없이 즉시 상태만 바뀐다.
- 보유기간 고지 문구는 항상 펼쳐진 상태로 보여준다. 아코디언으로 접어두지 않는다 — 법적 고지를 숨기는 UX는 만들지 않는다.

### 확인 다이얼로그 (이벤트 종료/삭제)

- `transform-origin: center`(트리거 위치 앵커링 없이 항상 화면 중앙) — 모달은 특정 버튼에서 튀어나오는 팝오버가 아니라 화면 전체에 대한 개입이므로 중앙 고정이 맞다(emil-design-eng "모달은 예외적으로 center 유지").
- 진입: `scale(0.95) + opacity 0` → `scale(1) + opacity 1`, 200ms, `--ease-out`. **`scale(0)`에서 시작하지 않는다** — 현실에는 무(無)에서 나타나는 사물이 없다.
- 배경 스크림(`rgba(17,24,39,0.4)`)으로 뒤 화면을 분리한다.

## 7. 모션

### 애니메이션을 넣을지 먼저 판단한다 (emil-design-eng 프레임워크를 이 프로젝트 요소에 적용)

| 요소 | 빈도 | 판단 | 근거 |
|---|---|---|---|
| 버튼 눌림 피드백 | 매우 잦음 | **넣는다** (누르는 즉시, 100~160ms) | 반응성의 기초, 아무리 자주 봐도 방해되지 않을 만큼 짧음 |
| 폼 검증 에러 표시 | 잦음 | 넣지 않는다(즉시 표시) | 지연되면 사용자가 이미 다음 칸으로 넘어간 뒤 |
| Toast 등장/퇴장 | 가끔 | 넣는다(250ms) | 갑자기 나타나면 놀람, 갑자기 사라지면 못 읽음 — 전환이 필요 |
| 이벤트 카드 호버 | 데스크톱 한정, 잦음 | 아주 미세하게만(그림자만, 120ms) | 과하면 목록 스캔을 방해 |
| 확인 다이얼로그 | 드묾(삭제/종료 시에만) | 넣는다(200ms, scale+opacity) | 맥락 전환을 부드럽게 알림 |
| **룰렛 결과 연출** | 참여자 1인당 이벤트당 1회 | **유일하게 긴 연출 허용**(회전 1회, 1.2~2초) | "가끔/최초 경험"에 해당 — 유일하게 감성적 임팩트가 목적인 화면(FR-1.10) |
| 관리자 테이블 정렬/필터 | 하루 수십 회 | 넣지 않는다 | 100+회/일 규칙과 동일 원리 — 관리자 업무 속도를 늦추면 안 됨 |
| 페이지(라우트) 전환 | 매번 | 넣지 않는다 | 참여자든 관리자든 페이지 이동은 빈번 — 지연으로 느껴짐 |
| 키보드로 트리거되는 동작(폼 Tab/Enter) | 매우 잦음 | **절대 넣지 않는다** | apple-design·emil-design-eng 공통 원칙 |

### 토큰

```css
:root {
  --duration-instant: 100ms; /* 버튼 눌림 */
  --duration-fast: 160ms;    /* 버튼 상태 전환 */
  --duration-base: 200ms;    /* 드롭다운, 모달, 배지 전환 */
  --duration-toast: 250ms;   /* 토스트 */
  --ease-out: cubic-bezier(0.23, 1, 0.32, 1);     /* 진입: 시작이 빠르고 응답감 있게 */
  --ease-in-out: cubic-bezier(0.77, 0, 0.175, 1); /* 화면 안에서의 이동 */
}
```

- **`ease-in`은 UI 전환에 쓰지 않는다** — 시작이 느려 굼떠 보인다(emil-design-eng).
- **일반 UI 애니메이션은 300ms를 넘기지 않는다.** 룰렛 결과 연출만 유일한 예외다.
- **`transform`/`opacity`만 애니메이션한다.** `width`/`height`/`padding`을 직접 움직이지 않는다(레이아웃·페인트 재계산 방지, emil-design-eng "성능 규칙").
- **`prefers-reduced-motion: reduce`**: 룰렛 회전 연출을 포함해 모든 이동·확대 애니메이션을 짧은 opacity 크로스페이드로 대체한다(FE-8 완료조건에 이미 명시된 요구사항과 동일). 색상 전환처럼 정보 전달용 변화는 유지한다.

```css
@media (prefers-reduced-motion: reduce) {
  * { animation-duration: 0.01ms !important; transition-duration: 120ms !important; }
}
```

### 이 프로젝트에는 적용하지 않는 것

`apple-design` 스킬은 드래그·스와이프·바텀시트처럼 제스처 기반 인터페이스를 위한 규칙(velocity handoff, rubber-banding, 모멘텀 투사 등)을 폭넓게 다루지만, 이 프로젝트에는 드래그로 조작하는 화면이 없다(경품 행 추가/삭제도 클릭 기반이지 드래그 정렬이 아니다). 해당 규칙들은 **의도적으로 채택하지 않는다** — 지금 없는 인터랙션을 위해 스프링 물리·포인터 캡처 코드를 미리 만들지 않는다(오버엔지니어링 금지).

## 8. 반응형

- 참여자용 7개 화면(로그인/회원가입/이벤트 목록·상세/룰렛 결과 + 마이페이지 2개)은 `768px` 기준 모바일 우선으로 만들고, 그 이상에서 여백과 그리드 컬럼 수만 늘린다(레이아웃 구조 자체를 바꾸지 않는다).
- 관리자 화면(로그인/이벤트 목록·등록·수정/참여신청 목록/동의메모)은 데스크톱 폭(`1120px`) 고정, 반응형 코드를 넣지 않는다.

## 9. 접근성 최소 기준

이 프로젝트는 접근성 전담 대응을 범위에서 제외했다(PRD 3절). 다만 아래는 "접근성 기능"이 아니라 정상적인 UI라면 당연히 갖춰야 할 기본값이라 별도 비용 없이 지킨다.

- 포커스 가능한 요소는 `:focus-visible`에 항상 보이는 아웃라인을 남긴다(마우스 클릭 시엔 숨기고 키보드 탐색 시에만 보이게).
- 상태는 색만이 아니라 텍스트 라벨과 함께 전달한다(6절 배지 참고).
- 터치 기기에서 `:hover` 스타일이 탭 시 오작동하지 않도록 `@media (hover: hover) and (pointer: fine)`로 감싼다.
- `prefers-reduced-motion`은 7절 기준을 그대로 따른다.

## 11. 구현 방식

- 새 UI 라이브러리·CSS 프레임워크(Tailwind, styled-components 등)는 도입하지 않는다. 위 토큰과 기본 리셋을 `frontend/src/styles/tokens.css` 1개 파일에 CSS 커스텀 프로퍼티로 선언하고 `main.jsx`에서 한 번만 import한다. 버튼처럼 여러 화면에서 재사용되는 공용 클래스는 `frontend/src/styles/button.css`로 분리해 사용하는 페이지에서 각자 import한다(실제 구현 결과 — 별도의 `global.css`는 만들지 않음).
- 컴포넌트별 스타일은 각 `.jsx` 옆에 동일 이름의 `.css`를 두는 일반 CSS 방식으로 충분하다 — 화면 수가 12개뿐이라 CSS Modules/CSS-in-JS 도입 비용이 이득보다 크다. 두 번째로 재사용되는 스타일이 실제로 생기면 그때 공용 클래스로 옮긴다(프로젝트 원칙 1절과 동일한 판단 기준. 실제로 버튼 스타일이 이 기준에 해당해 `styles/button.css`로 분리됨).
- 아이콘은 라이브러리를 새로 넣지 않고 필요한 만큼만 인라인 SVG로 직접 넣는다(화면당 1~2개 수준 — 뒤로가기, 닫기, 체크 정도).

## 12. 리뷰 체크리스트

FE 코드 리뷰 시 아래를 확인한다(emil-design-eng 리뷰 체크리스트를 이 프로젝트 기준으로 축약).

| 확인 항목 | 기준 |
|---|---|
| `transition: all` 사용 여부 | 애니메이션 속성을 명시했는가(`transform`/`opacity` 등) |
| `scale(0)`으로 시작하는 진입 애니메이션 | `scale(0.95)` 이상 + `opacity: 0`으로 시작하는가 |
| `ease-in` 사용 여부 | 진입/전환에 `ease-in`을 쓰지 않았는가 |
| 버튼에 `:active` 피드백이 있는가 | `scale(0.97)` 등 눌림 반응이 있는가 |
| 키보드 트리거 동작에 애니메이션이 있는가 | Tab/Enter 등에는 애니메이션이 없어야 한다 |
| UI 애니메이션이 300ms를 넘는가 | 룰렛 결과를 제외하고 넘지 않아야 한다 |
| 호버 애니메이션에 `hover: hover` 가드가 있는가 | 터치 기기 오탐 방지 |
| `prefers-reduced-motion` 대응이 있는가 | 이동/확대 애니메이션을 대체했는가 |
| 상태를 색으로만 구분하는가 | 텍스트 라벨이 함께 있는가(2절) |
| 새 색상/굵기/간격 값을 즉석에서 만들었는가 | 2~5절 토큰 밖의 값을 쓰지 않았는가 |

## 부록: 근거로 삼은 스킬

- **`apple-design`**(Designing Fluid Interfaces, WWDC): 반응 속도, 스프링 기본값, 타이포그래피의 크기별 자간/행간, `prefers-reduced-motion` 처리, 8대 디자인 원칙 — 1·3·7·9절에 반영
- **`emil-design-eng`**: 애니메이션 여부 판단 프레임워크, easing/duration 기준, 버튼·팝오버·토스트 컴포넌트 디테일, `transition` vs `keyframes` 선택 기준 — 6·7·12절에 반영
- **`pick-ui-library`**: 토스트 라이브러리(Sonner) 등 후보를 검토했으나, 이 프로젝트 규모에서는 직접 구현이 더 적합하다고 판단해 채택하지 않음(6절 Toast 참고). 향후 요구사항이 커지면 재검토 대상으로 남겨둔다.
- 드래그·제스처·머티리얼(반투명 레이어) 관련 규칙은 이 프로젝트에 해당 인터랙션이 없어 의도적으로 제외했다(7절 "적용하지 않는 것").
